Cloudflare 兩頭接

LINE Bot × OpenClaw 專案工程實作方案

用 Cloudflare Worker + Hono 當邊界層，前面安全接住 LINE webhook，後面提供受保護 API 給 OpenClaw 定期處理新聞、摘要與 polis 題目，讓整體資料流更穩、更清楚、更容易擴充。

  • Worker 負責驗證、整理、保護與記錄
  • OpenClaw 專心處理 AI 摘要與題目生成
  • LINE Bot 專注互動、推播與投票回收

專案目標

把「接收事件」與「AI 處理」分成兩條清楚的責任線

對外

接收 LINE Bot webhook、處理使用者互動、驗證 signature，避免惡意請求直接穿透系統。

對內

提供 OpenClaw 定期輪詢的內部 API，讓摘要、分類與題目生成有獨立節奏可控。

對營運

把資料整理、安全控管、記錄與狀態管理集中在 Worker，後續上線與除錯都更容易。

總體架構

一個 Worker，接住兩種方向完全不同的流量

輸入端

  • 新聞來源 / RSS
  • 手動匯入
  • LINE Webhook 事件

Cloudflare Worker + Hono

  • POST /line/webhook
  • GET /api/news/pending
  • POST /api/news/:id/process
  • GET /api/polis/payloads
  • LINE Signature 驗證
  • Token 驗證 / 日誌 / 節流

輸出端

  • LINE Bot 互動與推播
  • OpenClaw 定期排程
  • AI 摘要與 polis 題目生成

模組拆分

把系統分成三塊，讓每一塊只做自己擅長的事

A. LINE Webhook 入口

接收使用者訊息、按鈕與 postback，使用原始 body 驗證 x-line-signature，必要時把事件寫進 D1 或 KV。

B. OpenClaw 專用 API

提供待處理新聞、接收 AI 回寫、交付待投放的 polis 載荷，只允許帶正確 token 的客戶端存取。

C. 資料層

以 KV 處理簡單狀態與快取，以 D1 保存新聞、摘要、任務、使用者與 bot 事件，先滿足 MVP，再逐步擴充。

為什麼這樣設計

兩頭接，不只是接得上，而是接得穩

降低安全風險

LINE webhook 不直接打到 AI 流程，先由 Worker 進行驗證、過濾與紀錄，可以把攻擊面壓到最小。

邊界責任集中

Header 檢查、節流、日誌與 request 驗證都留在 Worker，系統錯誤點更容易定位與處理。

AI 任務更專注

OpenClaw 不必理解 LINE 平台細節，只需定期拉資料、產出摘要與題目，再把結果回寫即可。

安全設計

先把邊界守住，再談流程自動化

LINE Webhook 驗證

使用 channel secret 對原始 request body 做 HMAC-SHA256，與 x-line-signature 比對，失敗直接拒絕。

  • 一定使用原始 body
  • 先驗證再 parse
  • 失敗回 401 或 403

OpenClaw API 保護

最少先做三層：Bearer Token、來源識別、時間戳與簽章，避免未授權調用與重放攻擊。

  • Authorization: Bearer <TOKEN>
  • X-Client-Id 區分節點
  • X-Timestamp + X-Signature 進階保護

MVP API 規格

第一版先把最關鍵的四個入口釘穩

POST

/line/webhook

接收 LINE 平台 webhook，成功回 200 OK，簽章驗證失敗回 401 Unauthorized。

GET

/api/news/pending

由 OpenClaw 定期拉取待處理新聞，header 需帶共享 token。

POST

/api/news/:id/process

回寫 AI 摘要、關鍵字、polis draft 與狀態，讓 Worker 管理處理進度。

GET

/api/polis/payloads

提供後續投放流程所需的投票載荷，銜接審核、推播與投票機制。

資料流

從收集到投放，先建立一條最短可行的處理管線

01

收集

新聞從 RSS、手動匯入或 webhook 進入 news_items，狀態先標為 pending。

02

AI 整理

OpenClaw 用排程抓取待處理新聞，產生摘要、標題整理與 polis statements。

03

審核

加入 review_status，避免不適當題目直接流向使用者，提高內容品質與安全性。

04

LINE 投放

Worker 從 polis_tasks 取出可投放題目，透過 Messaging API 推送並回收互動結果。

實作順序

先把最值錢的事情做好，不急著把系統做滿

  1. 建立 Cloudflare Worker + Hono 專案骨架。
  2. 完成 POST /line/webhook 與 LINE signature 驗證。
  3. 加入 /api/* Bearer Token middleware。
  4. 建立 D1 schema，先落 news_items 與 ai_summaries。
  5. 讓 OpenClaw 能抓待處理新聞並回寫摘要。
  6. 最後再接 LINE 推播與 polis 投票資料流。

一句話總結

用 Cloudflare Worker + Hono 當邊界層，前面接 LINE Bot，後面開受 Token 保護的 API 給 OpenClaw 定期呼叫，會比讓 LINE 直接碰 OpenClaw 更安全，也更容易維護。
